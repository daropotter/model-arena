# Returns feature contract

Ship a complete return/refund workflow in the existing Orders product.
The delivered bundle contains `dist/orders.pyz`, `dist/worker.pyz`,
`dist/refunds.mjs` and `dist/payment-contract.json`, built by `python3 build.py`
from `src/`, `client/` and `config/`. Read DISTRIBUTED.md and RELEASE.md too. The build must be deterministic and standalone: it must run
with no source checkout, downloads or PYTHONPATH. Python standard library
is sufficient. Preserve the existing visible tests, seed fixtures and old
consumer; add tests under `tests_extra/`.

## Database upgrade and old product

Existing databases use `fixtures/seed.sql`, schema version 1. Implement
`python3 dist/orders.pyz migrate --db PATH`: additive, transactional upgrade
to `PRAGMA user_version=2` for release ABI1 and version 3 for ABI2.
ABI2 supports both version 1 and 2 inputs. All upgrades are safe to rerun
including after returns and pending payouts exist.
Preserve every old order, line, inventory quantity and original total.
New tables/columns are your choice. All request state, request keys, audit
history and refund ledger must survive process restart and repeat migration.
Use transactions for mutations, including concurrent requests.

`orders.total_cents` and each `order_items.paid_cents` are integers after
all discounts/taxes. `paid_cents` is the amount for the WHOLE line, not one
unit. The sum of paid line amounts equals the order total. `quantity` is
the original purchased count. Currency is read from the order. Existing
inventory rows exist for every sold SKU.

Keep `GET /v1/orders/ID` exactly compatible: an object with only `id`,
`status`, `currency`, `total_cents`. The original order total/status never
changes because of returns. `clients/legacy.py` must still work against
both old and new builds. Health stays `GET /health` returning 200.

## Local identities and permissions

The exercise uses synthetic bearer identities `TENANT:ROLE:USER`. Allowed
tenants are alpha/beta; roles are customer/support/warehouse/finance.
Missing/malformed identities return 401. No real authentication provider
or money transfer is required.

Customer reads, lists and creates only for their own orders. Customers can
cancel their own requested returns. Support approves or rejects;
warehouse receives; finance settles. Staff read any order/return in their
own tenant. Finance alone reads the refund ledger and CSV export.
A wrong role returns 403. An existing ID in another tenant or another
customer's order/return is indistinguishable from a missing ID (404),
before testing mutation permission. Tenant order IDs and request keys may
coincide; their state is independent. Rejected/unauthorized operations
leave the complete database unchanged.

## API and transitions

All new endpoints return JSON, except CSV. Error responses are JSON objects
with an `error` string. Extra diagnostic fields are permitted. The following
status codes and successful fields are part of the public contract.

`POST /v2/returns` takes exactly:

```json
{"order_id":"o1","request_key":"request-1","reason":"Too small","items":[{"sku":"book","quantity":1}]}
```

The three string fields must be nonblank, at most 200 characters. `items`
is a nonempty array; each element has exactly `sku` (nonempty string) and
`quantity` (positive integer, NOT bool/float). Duplicate or unknown SKUs
are invalid. Invalid payload/items return 400 atomically. An unpaid order
returns 409. The order must exist and belong to this customer.

A successful new request returns 201 with at least `id`, `order_id`,
`status`, `reason`, `refund_cents`, and `items`. Items are sorted by SKU;
new status is `requested`, new refund is 0. Each item has `sku` and
`quantity`. IDs are opaque and generated by the service.

`request_key` is scoped to tenant+customer. The same key and semantically
same payload (including reordered items) returns 200 and the CURRENT
representation of the original return. Changed payload on the same key
returns 409. Key replay and action replay never duplicate state, inventory,
audit events or money. Concurrent identical requests yield exactly one 201
and the rest 200, all with the same ID.

`GET /v2/returns/ID` returns that object. `GET /v2/returns?order_id=ID`
returns `{"returns":[...]}`, sorted by return ID. Missing `order_id` is 400.
`POST /v2/returns/ID/ACTION` uses an empty JSON object:

| Action | Role | From | To |
|---|---|---|---|
| cancel | customer (owner) | requested | cancelled |
| approve | support | requested | approved |
| reject | support | requested or approved | rejected |
| receive | warehouse | approved | received |
| settle | finance | received | pending_refund |

Success is 200 with the current return object, except settle: 202 when
pending (including replay), 200 when already refunded. Repeating the action when
already in its target state is a successful no-op, after permission checks.
Every other transition is 409. Cancelled/rejected returns are terminal.

Requested, approved, received, pending_refund AND refunded quantities count against the
purchased quantity. Cancelled/rejected quantities do not. Over-reservation
returns 409 even under simultaneous requests. Receiving adds quantities
to tenant inventory exactly once. Cancelling/rejecting does not add stock.
Settling atomically writes a durable payout intent with a fixed amount and
provider key; it does not call the provider or write the refund ledger.
The separate worker completes payment, writes one ledger entry and fills
`refund_cents`. Until then refund_cents is 0. See DISTRIBUTED.md.

For each SKU, let P be original line paid_cents, Q original quantity,
s units in pending_refund OR refunded before this enqueue, and q this
return's units. Failed/dead payouts remain pending_refund and reserve cents.
The refund is `floor((s+q)*P/Q) - floor(s*P/Q)`. Sum these differences across
SKUs. Serialize concurrent settlements. For 3 units paid 1000 cents,
three single-unit settlements refund 333, 333, 334; at 1001 they refund
333, 334, 334. Multiple partials must never overpay. Use integer arithmetic.

## Accounting, audit, switches and client

`GET /v2/returns/ID/events` returns `{"events":[{"action":"create",
"actor":"alpha:customer:alice"},...]}` in event order. Record exactly one
event for create and every successful state transition; paid is recorded
by TENANT:worker:payouts. Automatic retries and rejected operations add no
events. Explicit finance retry of a dead payout records one retry event. Apply the same read isolation as for returns.

`GET /v2/ledger` returns `{"entries":[{"return_id":"...",
"amount_cents":333,"currency":"PLN"}]}`, sorted by return ID and scoped
to the finance user's tenant. Pending returns never appear.

`GET /v2/refunds.csv` exports only settled refunds in return-ID order.
Header: `return_id,order_id,currency,refund_cents,reason`. Use standard CSV
quoting for commas, quotes, Unicode and newlines. No cross-tenant rows.

`serve --returns off` returns 503 for all return mutations, without side
effects. Existing reads, legacy API, ledger and export remain available.
Restarting with `--returns on` restores mutations without losing data.

The built executable must also provide this HTTP client (no internal DB
access or server imports to perform the request):

```
python3 dist/orders.pyz client BASE TOKEN create ORDER KEY REASON SKU QTY [SKU QTY ...]
python3 dist/orders.pyz client BASE TOKEN get RETURN_ID
python3 dist/orders.pyz client BASE TOKEN action RETURN_ID ACTION
python3 dist/orders.pyz client BASE TOKEN list ORDER
python3 dist/orders.pyz client BASE TOKEN export
```

Print the JSON response or CSV to stdout, exit 0 on HTTP success; exit
nonzero on errors. Preserve quoted/multiline reasons and server errors.

Fixtures are examples, not the only accepted amounts or identifiers.
Implement general behavior. Acceptance checks probe the built HTTP product,
concurrent requests, client process and physical database side effects.
